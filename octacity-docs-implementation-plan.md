# Octacity Docs — Implementation Plan

## 1. Goal

Build a Turkish-first, opinionated documentation website for Octacity using Docusaurus.

The implementation should optimize for:

- excellent reading experience,
- low maintenance cost,
- simple contribution workflow,
- fast static delivery,
- strong GitHub integration,
- room for light Octacity branding,
- and minimal unnecessary customization.

The content is the product. Docusaurus is infrastructure.

---

# 2. Technology Choice

## Framework

Use the latest stable Docusaurus release.

Preferred stack:

- Docusaurus
- TypeScript
- Markdown / MDX
- Node.js LTS
- npm, pnpm, or the package manager already preferred by the repository owner
- GitHub Actions
- GitHub Pages or the final Octacity-controlled static host

Do not add additional frontend frameworks.

Use React only where Docusaurus requires it.

The site should remain mostly Markdown-driven.

# 5. Phase 1 — Bootstrap

## Tasks

1. Create the repository.
2. Initialize Docusaurus with TypeScript.
3. Remove example/tutorial content.
4. Remove the blog feature unless there is an explicit future need.
5. Remove unnecessary default pages and assets.
6. Configure Turkish as the default locale.
7. Configure project metadata:
   - title: Octacity Docs
   - tagline: short practical description
   - favicon
   - organizationName
   - projectName
   - repository URL
8. Configure clean production URLs.
9. Set up local development commands.
10. Add a minimal README for contributors.

## Acceptance criteria

Running the development server should open a clean, empty Octacity Docs shell with no Docusaurus tutorial/demo content.

# 6. Phase 2 — Navigation and Information Architecture

Create the seven agreed sections:

1. Başlangıç
2. GitHub ile Çalışmak
3. Takım Olarak Çalışmak
4. Maintainer Rehberi
5. Açık Kaynak
6. Release ve Proje Sağlığı
7. Octacity Bağlamı

Use autogenerated sidebars only if the ordering remains predictable and easy to control.

Otherwise define explicit sidebar categories in `sidebars.ts`.

Recommended behavior:

- collapsible section navigation,
- current page highlighted,
- table of contents on content-heavy pages,
- previous/next navigation,
- breadcrumbs enabled,
- mobile sidebar works without customization.

Do not introduce a custom navigation system unless Docusaurus becomes a real blocker.

# 8. Phase 4 — Visual Identity

The goal is recognizable Octacity branding without turning the project into a custom frontend.

## Customize

- Octacity logo
- typography if necessary
- spacing
- accent color
- navbar
- footer
- code block appearance
- admonition appearance
- light/dark mode polish
- social preview image

## Avoid initially

- deep theme swizzling,
- custom routing,
- custom layout engine,
- animated landing pages,
- complex React components,
- visual effects that hurt reading performance.

The design should feel like documentation first.

# 10. Search

Search should be present early because the product is intended as a “look it up when stuck” knowledge base.

## Initial options

Preferred order:

1. Docusaurus-compatible local/static search if quality is sufficient.
2. Algolia DocSearch if the project becomes eligible and external indexing is acceptable.
3. Another lightweight Docusaurus-compatible search solution.

Requirements:

- Turkish text must index correctly.
- Titles and headings should rank strongly.
- Search should work on static deployment.
- Search should not require unnecessary backend infrastructure.

Search is more important than elaborate homepage design.

# 11. Markdown / MDX Conventions

Use Markdown for almost all content.

Use MDX only when a guide genuinely benefits from a reusable interactive or visual component.

Recommended built-in Docusaurus features:

- admonitions
- tabs
- code blocks
- syntax highlighting
- heading anchors
- frontmatter
- links

Do not introduce custom components for content that can be expressed cleanly in Markdown.

---

# 12. Frontmatter Convention

Recommended minimal frontmatter:

```yaml
---
title: İyi bir Issue nasıl yazılır?
description: Bir GitHub Issue'yu başka bir geliştiricinin doğrudan çalışmaya başlayabileceği kadar açık hale getirmek.
sidebar_position: 1
---
```

Optional metadata later:

```yaml
tags:
  - github
  - collaboration
```

Avoid complex content schemas until there is a demonstrated need.

---

# 13. Links to Official Octacity Sources

Where a topic crosses into governance or policy, link to the relevant source in `octacity-org/.github`.

Example:

```md
Bu sayfa pratik kullanım önerileri içerir.

Octacity'nin resmi contribution kuralları için:
[octacity-org/.github](...)
```

Never copy official rules into the docs unless there is a compelling technical reason.

This prevents drift between two sources of truth.

---

# 14. GitHub Contribution Workflow

Docs should be editable like code.

Recommended workflow:

```text
Issue / idea
→ branch
→ Markdown change
→ Pull Request
→ review
→ merge
→ automatic deployment
```

For tiny typo fixes, maintainers may use GitHub’s direct editing interface depending on repository policy.

Add:

- `CONTRIBUTING.md`
- PR template only if useful
- issue template for “new guide suggestion” only if recurring requests justify it

Do not over-process documentation contributions.

---

# 15. Quality Checks

Add lightweight CI.

Recommended checks:

1. Docusaurus production build
2. Broken internal links
3. Broken anchors
4. TypeScript errors
5. Markdown linting only if rules are kept minimal
6. Optional spelling/language checks later

Avoid introducing a large documentation toolchain in v0.1.

A failed docs build should block deployment.

---

# 16. Deployment

Preferred initial deployment:

## Option A — GitHub Pages

Advantages:

- simple,
- free,
- native to the repository,
- appropriate for static Docusaurus output.

Set up GitHub Actions deployment from the default branch.

## Option B — Custom Octacity domain later

Possible future URL:

```text
docs.octacity.dev
```

or whichever Octacity domain becomes canonical.

Do not make the initial launch depend on obtaining or restructuring domains.

---

# 17. Performance

Documentation should feel immediate.

Requirements:

- static generation,
- optimized images,
- no unnecessary client-side JS,
- avoid heavyweight custom components,
- keep custom CSS small,
- test mobile rendering,
- test navigation without animations becoming a blocker.

Docusaurus defaults should be preferred until measured evidence shows a problem.

---

# 18. Accessibility

Baseline requirements:

- semantic heading order,
- keyboard-accessible navigation,
- readable contrast,
- visible focus states,
- alt text for informative images,
- avoid text embedded inside images,
- respect reduced-motion preferences.

Do not break Docusaurus accessibility behavior through unnecessary customization.

---

# 19. Analytics

Do not add analytics by default.

If analytics are introduced later, define the question first.

Examples:

- Which guides are searched most?
- Which pages have no useful entry traffic?
- What questions produce zero-result searches?

Prefer privacy-respecting analytics if analytics becomes useful.

---

# 20. Versioning

Do **not** enable Docusaurus documentation versioning initially.

Octacity Docs is a living knowledge base, not API documentation.

The current guide should normally represent the current recommendation.

Use Git history for historical versions.

Enable formal docs versioning only if a future use case actually requires multiple simultaneously supported knowledge states.

---

# 21. Internationalization

Start Turkish-first.

Do not build an English mirror immediately.

Docusaurus i18n support can be introduced later if:

- non-Turkish Octacity members need the content,
- the docs develop external readership,
- or English becomes useful for broader open-source distribution.

Content architecture should avoid assumptions that make future localization difficult.

---

# 22. Phase 5 — Feedback Loop

After launch, observe actual usage.

When a recurring question appears:

1. Check whether an existing guide already answers it.
2. Improve that guide if the answer is unclear.
3. Create a new guide only if the question is meaningfully distinct.
4. Link related pages.
5. Use real examples when possible.

The docs should grow from problems, not from a desire to fill categories.

---

# 23. Deferred Features

Explicitly out of scope for v0.1:

- documentation versioning
- blog
- custom CMS
- comments
- user accounts
- custom search backend
- AI chatbot
- complex interactive diagrams
- custom React design system
- custom documentation compiler
- custom Markdown parser
- custom router
- multilingual content
- offline/PWA mode
- analytics
- automatic AI-generated guides

These can be reconsidered only after the base docs are useful.

# 25. Definition of Done for v0.1

Octacity Docs v0.1 is ready when:

- the production site is publicly accessible,
- Turkish is the default language,
- the seven sections are visible,
- the initial 15 guides exist,
- search works,
- navigation is usable on desktop and mobile,
- official Octacity governance is linked rather than duplicated,
- GitHub contribution instructions exist,
- the site builds and deploys automatically,
- there are no known broken internal links,
- and a member can realistically use the site to answer common project-development questions without asking someone directly.

---

# 26. Agent Handoff Summary

If this plan is handed to an implementation agent, the agent should:

1. Build the Docusaurus site, not redesign the content strategy.
2. Keep customization minimal.
3. Do not add features outside the stated scope.
4. Treat Markdown content as the primary interface.
5. Preserve the distinction between practical guidance and official Octacity governance.
6. Prefer Docusaurus-native behavior over custom React code.
7. Make the site fast, readable, searchable, and easy to contribute to.
8. Stop at a clean v0.1 rather than turning the task into a custom docs platform.
